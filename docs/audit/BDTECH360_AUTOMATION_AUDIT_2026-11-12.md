## Architecture and preservation baseline

- Existing app: Next.js 16 App Router, Node 22, React 19, TypeScript, Prisma/MySQL; public website, hash-routed admin and portal, and API routes share the same application. Public contact form posts to `/api/contact`; webchat posts to `/api/chat/*`; admin screens use same-origin `/api/admin/*` endpoints. Auth/roles/CSRF are in `src/lib/auth.ts`, `src/lib/api-guard.ts` and `src/lib/access-policy.ts`. `src/proxy.ts` and `next.config.ts` contain request and routing configuration.
- `prisma/schema.prisma` has customer, lead, communication, scope, approval, preview, project, payment, delivery, identity, audit, queue, agent and factory models; `prisma/migrations/` contains the published MySQL migrations. Preserve all existing rows, identifiers, schema and migration history. Any future migration must be additive and tested on a disposable MySQL copy first.
- `npm run build` generates Prisma, reconciles migrations, runs `migrate deploy`, builds Next standalone, and copies assets. **Never run it with production credentials for local validation**. `.github/workflows/ci.yml` uses disposable MySQL; Hostinger Git integration is the documented deployment target, but the current live deployment and startup configuration are not verified. Legacy deployment paths are documented as retired.
- Preserve existing URLs, brand, frontend, portal, auth, roles, APIs, database records, provider selection and governance. No production changes, data resets, credentials, or live sends were performed.

## File-by-file controlled implementation plan (not yet executed)

Before changes: finish reviewing all affected routes, their callers and existing tests, establish lifecycle evidence/provenance, map all source/export and payment entry points, and compare real deployment/configuration with the repository. Obtain a disposable MySQL environment and production-equivalent Prisma engines. Do not infer missing functionality from UI or registry declarations.

1. **Preview correctness first**: inspect and then change only `src/lib/journey.ts` embedded response handling, `src/app/api/preview/[token]/action/route.ts` transaction/idempotency logic, and relevant `tests/preview-policy.test.ts` plus a route-level regression test. Test HTTP failures, duplicate/concurrent decisions and the persisted event/communication side effects. Avoid reporting success if a decision is not persisted. Verify legacy preview links remain valid.
2. **Lifecycle enforcement**: after mapping all payment/preview paths, design a shared policy in `src/lib/lifecycle-policy.ts` or existing policy module, wire it into `src/lib/journey.ts` and `src/app/api/payments/stripe/checkout/route.ts` plus any other verified payment entry points; add targeted integration tests. Define how existing customers and legacy invoices are handled before enforcing. Require explicit scope approval and actual preview delivery evidence without making old data unusable; retain payment and handover controls. A real project HTML preview may require an artifact pipeline, not just scope HTML.
3. **Webhook recovery**: inspect `src/app/api/webhooks/whatsapp/route.ts`, `src/lib/identity-resolver.ts` and existing webhook tests; plan batch iteration and provider retry behavior with duplicate-side-effect tests, including crash/lease and uncertain outbound sends. Review Hostinger semantics separately in `src/app/api/webhooks/hostinger-mail/route.ts` and `tests/hostinger-mail-webhook-route.test.ts`; do not assume undocumented provider retry behavior or blindly retry ambiguous sends.
4. **Identity and chronology**: trace contact, webchat, WhatsApp, Hostinger and portal ownership proofs; extend `src/lib/identity-resolver.ts` and communication APIs only where evidence warrants it. Preserve existing IDs; design strict TECH format/overflow and backward compatibility in `src/lib/ids.ts` and tests without renumbering clients. Verify chronological history across stores and conflict handling.
5. **Agent permissions and automation**: trace `src/lib/agents/{registry,engine,orchestrator,jobs,tool-executor}.ts`, `src/lib/ops-loop.ts`, `src/lib/events/bus.ts`, `src/lib/workflows/definitions.ts`, governance and existing n8n paths. Reuse the existing queue; implement only bounded, idempotent agent actions that can enforce tenant scope and authorization. Keep payment approval, sanctions/legal decisions human-controlled; avoid broad blanket approval for routine replies only after policy and safety tests prove it safe. Verify scheduler/heartbeat and alert recovery before enabling autonomous actions.
6. **Integration rollout**: keep Gmail separate; review Hostinger/WhatsApp/AI provider settings without revealing values. In an authorized staging environment use operator-owned internal test accounts to exercise actual send, receive, webhooks, replay, failures, auth and Super Admin checks. Do not send live customer messages or configure production services without approval.
7. **Change control**: every batch gets targeted tests, full lint/typecheck/tests, production build on disposable MySQL, migration/drift and rollback checks. Add only additive migrations if necessary. Review each diff; document files and migration, and commit to the current branch only once required checks pass. Revert a reviewed commit to roll back code; for additive database changes retain historical data and use a tested backup/restore procedure, never a reset. No deployment without explicit authorization.
