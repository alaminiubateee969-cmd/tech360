# Tech360 — Hostinger environment configuration

Checked against repository code: 2026-10-24. This is a configuration guide, not proof that the deployed integrations work.

**Start with `docs/HOSTINGER-ENV-TEMPLATE.txt`.** It includes all `.env.example` variables and contains placeholders only. Replace every `REPLACE_*` value before deployment. No real credentials are supplied. Never paste passwords or API keys in chat or commit a completed template.

## 1. Where to enter values

In the Hostinger **Node.js Web App** environment-variable settings, add each NAME and VALUE separately. Do not paste comments or `NAME=` into a value. In hPanel fields use the raw value without surrounding dotenv quotes. If importing a `.env` file, use proper dotenv quoting for spaces and special characters, and keep that file private outside `public/`.

Use Node **22.x**, the repository root, `npm run build`, and the repository production start command **`npm start`**. Confirm in runtime logs that startup validation executes; the repository cannot confirm the current Hostinger preset's invocation behavior. Keep Hostinger's assigned `PORT`; do not override it with a guessed port. Bind the Node server to `0.0.0.0` if your hosting configuration requires a host setting. No `NEXT_PUBLIC_` variable should contain a secret.

These session changes are on `arena/71693fb1-tech360`. A Hostinger deployment watching `main` will not receive them until they are reviewed/merged into its configured deployment branch. This guide does not change or push your deployment branch.

Generate EACH application-owned secret independently on a trusted local terminal:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Run again for each secret. Do not reuse secrets or use the literal template strings. Keep secure backups. Do not replace existing `IDENTITY_HASH_SECRET` casually. Provider-issued webhook signing secrets must come from the provider, not this command.

**Important AI limitation:** the main journey engine uses `createZaiClient()` and the configured compatible provider. `OPENROUTER_API_KEY` enables the separate command-center assistant only. Setting it does not replace `ZAI_API_KEY`, wire arbitrary providers into the journey, or guarantee free usage. A generic OpenAI-compatible URL is not automatically compatible with every request field used by the main engine; validate real agent calls.

## 4. Email — choose SMTP OR Hostinger Mail API

### Recommended simple mailbox SMTP configuration

Use the mailbox's actual **SMTP settings from hPanel**. The Node app's environment does not create a mailbox.

```dotenv
HOSTINGER_MAIL_ENABLED=false
SMTP_HOST=REPLACE_WITH_MAILBOX_SMTP_HOST
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=info@bdtech360.com
SMTP_PASS=REPLACE_WITH_MAILBOX_PASSWORD
SMTP_FROM=info@bdtech360.com
PORTAL_OTP=on
PORTAL_OTP_CHANNEL=email
```

For a provider that documents port 587 with STARTTLS, use `SMTP_PORT=587` and `SMTP_SECURE=false`. Do not combine port 587 with TLS-on-connect just because it sounds safer. Confirm actual mailbox login, sender permissions, SPF, DKIM and DMARC in your mail/DNS settings. Production requires portal OTP even if you try to set it off; configure a working email/SMS/WhatsApp channel.

`EMAIL_WEBHOOK_SECRET`: separate random 32+ character inbound relay secret. The generic email endpoint is `/api/webhooks/email`; the relay must authenticate using the supported raw-body HMAC headers or `x-email-webhook-secret`. An SMTP configuration alone cannot receive incoming email; you also need a compatible inbound forwarding/relay service.

### Optional Hostinger Mail API mode

Only enable when you have the actual managed mailbox API resource and token:

| Variable | Value |
| --- | --- |
| `HOSTINGER_MAIL_ENABLED` | Exactly `true` |
| `HOSTINGER_MAIL_API_TOKEN` | Narrowly scoped Hostinger Mail API token, not your account password |
| `HOSTINGER_MAILBOX_RESOURCE_ID` | Actual mailbox resource ID, not the mailbox email address |
| `HOSTINGER_MAIL_FROM_ADDRESS` | Actual managed mailbox address on `bdtech360.com` |
| `HOSTINGER_MAIL_WEBHOOK_SECRET` | If using its webhook: one-time provider-issued signing secret, at least 32 characters; preserve the real value returned by the authorized setup |

Webhook: `/api/webhooks/hostinger-mail`. When enabled but invalid, this mode refuses email sends rather than silently falling back to SMTP. `HOSTINGER_MAIL_REPLY_TO` is not supported/read.

## 6. SMS and portal OTP

### httpSMS / device gateway

- `HTTPSMS_API_KEY`: actual gateway key.
- `HTTPSMS_FROM`: the actual connected phone/SIM number in international format.
- `HTTPSMS_BASE_URL`: real gateway base URL, accessible from the server (e.g. a provider's documented URL). A self-hosted gateway must be deployed separately.

An Android device/SIM gateway needs a running connected device and carrier service; it is not unlimited free SMS. Set all three for consistency across the app's SMS and call-centre paths.

### Generic outbound SMS adapter

- `SMS_API_URL`: actual provider's compatible send endpoint.
- `SMS_API_KEY`: actual key.
- `SMS_SENDER`: provider-approved sender value where supported.

The provider must match the request shape expected by `src/lib/comms.ts`; pasting any arbitrary SMS service URL is insufficient.

### Other telephony fields

- `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`: actual Twilio account credentials for relevant telephony/signature paths.
- `TWILIO_FROM_NUMBER`: template entry; do not assume this alone enables outbound Twilio calling/SMS. The audited call-centre code mainly derives configuration state, dial links and device SMS behavior.
- `SIP_DOMAIN`: your actual SIP/softphone domain; requires a working SIP service/client, not just a hostname string.
- `PORTAL_OTP_CHANNEL`: `email`, `sms`, or `whatsapp`; preference, not a substitute for the corresponding configured adapter.

Inbound SMS endpoint: `/api/webhooks/sms`. **Security limitation:** current code verifies Twilio signatures when supplied, but does not universally reject unsigned generic inbound messages. No `.env` variable fixes that. Do not expose unrestricted generic SMS ingress; restrict it at a trusted authenticated proxy/relay and harden signature enforcement before production acceptance.

## 7. Social channels and automation relays

- `SOCIAL_WEBHOOK_SECRET`: separate random shared secret for the authenticated social relay.
- `FACEBOOK_PAGE_TOKEN`, `INSTAGRAM_TOKEN`, `LINKEDIN_TOKEN`, `X_TOKEN`: actual service credentials only when applicable. These presence flags are not proof of native outbound implementations or approved account access.
- `N8N_WEBHOOK_BASE`: real reachable n8n webhook base used by the app.
- `N8N_WEBHOOK_SECRET`: distinct random shared secret; use the matching secret in your n8n workflow.
- `NOTIFY_RELAY_URL`, `NOTIFY_RELAY_TOKEN`: optional actual notification relay endpoint/authentication token; omit if unused.

Social relay endpoint: `/api/webhooks/social` with `x-webhook-secret`, accepted source channels FACEBOOK, MESSENGER, INSTAGRAM, LINKEDIN, X. This is not a direct drop-in Meta webhook format; your relay must transform the provider event to the route's expected payload and preserve a stable message ID.

n8n callback: `/api/webhooks/n8n`; configure authentication as implemented by that route. n8n hosting, workflows, provider app subscriptions and permissions must be set up separately. No Gmail/Google Calendar/Drive credentials are read by this app simply because those apps are connected in the coding conversation.

## 11. Backups — requires host filesystem and a real scheduled job

- `BACKUP_DIR`: actual writable persistent backup directory **outside** `public/`, `.next/` and the web root.
- `TECH360_BACKUP_DIR`: optional alias/runner configuration; if using both, keep aligned with your actual backup setup.
- `TECH360_BACKUP_OFFSITE`: optional configured destination, e.g. `rclone:remote:path` or `scp:user@host:/path`, with credentials in the backup runner's secure store.
- `TECH360_BACKUP_ALERT_WEBHOOK`: optional actual protected failure-alert receiver.
- `BACKUP_SCHEDULE`: declared schedule shown in the console; it does not create cron.
- `BACKUP_SCHEDULE_NOTE`: operator-facing description.

Do not invent a `/home/...` path from this guide; use the path granted to your actual Hostinger account. Check persistent-storage support. Schedule the backup scripts where MySQL tools, shell access, permissions, off-site tools and retention are available. Test a restore. See `docs/BACKUP_AND_RESTORE.md`.

## 12. Do not set in production

- `PREVIEW_SQLITE_URL`: explicitly refused in production.
- `E2E_ADMIN_EMAIL`, `E2E_ADMIN_PASSWORD`, `E2E_PORT`: local/CI testing, not production login setup.
- `NEXT_PHASE`, `NEXT_RUNTIME`: framework internals, not manual app configuration.
- `GITHUB_TOKEN`, `GH_TOKEN`: repository/tooling access, not required for public application runtime; use Hostinger's Git integration rather than granting the web app an unnecessary repo token.
- `TECH360_BASE_URL`, `TECH360_EXTRA_CA`: verification/tooling overrides, not replacements for canonical app origin.
- `XDG_CACHE_HOME`: optional tooling cache path, not business configuration.
- Placeholder `REPLACE_*` strings or any `NEXT_PUBLIC_*` API/password secret.

## 13. Acceptance checklist — required for “all functions working”

1. Replace required placeholders, save variables in hPanel, redeploy/restart.
2. Run `npm run start:check` in the production environment; it validates names/formats, not provider connectivity.
3. Run `npm run build` with a reachable MySQL database. The repository build includes Prisma generation/migration deployment; arrange a backup before production migrations.
4. Confirm production runtime startup, HTTPS apex domain and `GET /api/health` returning database UP.
5. Seed the first owner account once under controlled access, remove bootstrap password, log in and finish password/security setup.
6. Test portal OTP and actual outbound email/WhatsApp/SMS; check provider callbacks and CRM storage, including duplicate inbound messages.
7. Test a real agent run and successful queue work. Inspect Command Center pipeline monitor and AI operations heartbeat; merely ACTIVE is not end-to-end acceptance.
8. Exercise final scope approval, preview client approval, partial/failed/full payment, file-release approval, actual delivery and client acceptance. Never bypass approval/payment gates to make a demo look successful.
9. Test backup AND restore and inspect real provider billing/quotas.
10. Run the database-dependent tests against a disposable test database, not your production customer database.

**Environment setup is necessary, not sufficient:** unavailable external APIs, unsigned inbound SMS, incomplete adapters, missing deployed workflows, actual project development and unverified provider account permissions cannot be solved by filling `.env` fields.
