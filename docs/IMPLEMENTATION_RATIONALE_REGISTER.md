# TECH360 implementation rationale register

**Updated:** 2026-11-17 UTC
**Purpose:** Make the reasons for the existing implementation choices findable and reviewable. This register documents the current product scope; it does not add features, change policy, or authorize external integrations.
**Source of truth:** The referenced implementation, policy, test and operations documents remain authoritative for details. Paths in the register are repository-root-relative. Historical documents are labelled as such and are not production evidence by themselves.

A rationale is recorded at the subsystem/decision level rather than repeated beside every routine line of code. Security-sensitive or surprising behavior should additionally have a code comment and regression test near the implementation. `PASS` in a source test means code behavior was checked; it does not prove a live provider or Hostinger configuration works.

## Implementation decisions and why they exist

| ID | Existing implementation | Rationale / trade-off accepted | Why common alternatives were not selected | Canonical rationale and verification |
|---|---|---|---|---|
| IR-01 | Next.js App Router, React/TypeScript and standalone Node server | Keep public web pages and same-origin APIs in one deployable app and use the repository's established TypeScript safety and component system. | Do not add a second frontend or independently deployed API for the same user journey; that would add origin, auth, cookie and release coordination without a current requirement. | `README.md`; `docs/HOSTINGER_DEPLOYMENT.md`; route and build checks in `.github/workflows/ci.yml`. |
| IR-02 | Hostinger Node.js Web App, Node 22, npm and Git integration | Hostinger is the selected production owner; the app's Node/Next runtime and Hostinger build contract are explicit. | Retired VPS/SSH/Bun/Docker/Cloud Run paths could deploy a different revision or bypass Hostinger's lifecycle and must not compete with the selected path. | `docs/HOSTINGER_DEPLOYMENT.md`; `DEPLOYMENT.md`; PR #9 disposition in `docs/REPOSITORY_AUDIT_2026-11-17.md`; `tests/retired-deployment-paths.mjs`. |
| IR-03 | Prisma + MySQL with committed, ordered migrations | MySQL is the production database target; migrations make schema evolution reviewable and repeatable and preserve production data. | Do not use SQLite as production, `db push`, reset, or rename published migrations: those can diverge from MySQL or cause already-migrated databases to fail. SQLite remains an isolated test adapter only. | `DATABASE_SCHEMA_AND_MIGRATION_GUIDE.md`; `docs/HOSTINGER_SSH_RECOVERY.md`; `scripts/check-migration-immutability.mjs`; schema and MySQL CI jobs. |
| IR-04 | Fail-closed production startup and value-free env register | Catch missing/malformed critical settings before serving requests without printing secret values; keep Hostinger-specific values under operator control. | Do not hard-code guessed database endpoints, create placeholder keys, or silently continue with fake integrations. | `scripts/validate-production-env.mjs`; `.env.example`; `docs/HOSTINGER_ENVIRONMENT_VARIABLES.md`; startup validation tests. |
| IR-05 | One shared application session/auth and server-enforced RBAC, CSRF, rate limits and audit events | Protect all private operations at the server boundary and ensure UI visibility is not the permission check. | Client-only guards and role-hidden buttons do not protect APIs; granting portal access from a Client ID or unverified contact detail is unsafe. | `SECURITY.md`; `docs/AI_VISIBILITY_POLICY.md`; role-policy tests and protected-route tests. |
| IR-06 | Separate public marketing site from private admin/agent operations | Public pages should explain customer value without exposing internal prompts, agent inventory, operational controls or customer data. | Do not disclose control-plane implementation as public marketing content or expose internal APIs to anonymous users. | `docs/AI_VISIBILITY_POLICY.md`; README; public route and anonymous-auth tests. |
| IR-07 | Consent-based CRM intake; anonymous visitors can receive a prospect Client ID; raw email/phone is not identity proof | Reduce friction for visitors who want to chat without an account while protecting existing customer records from account-takeover-by-email. Keep contact consent separate from marketing consent. | Do not force an email to use WebChat, merge CRM rows on typed email alone, or infer marketing consent from a service enquiry. | `src/lib/chat-onboarding.ts`; `docs/CLIENT_COMMUNICATION_DOCUMENT_VAULT.md`; `tests/contact-consent-evidence.test.ts`; `tests/tech360-messaging-repair.test.ts`. |
| IR-08 | Public WebChat uses same-origin routes and an HMAC-signed, HttpOnly, SameSite cookie bound to anonymous visitor ID | Persist a web conversation without a vendor widget or cross-origin token exposure; allow the visitor to read/write only their own consented thread. | A client-supplied anonymous ID alone is guessable/forgeable; exposing a bearer secret to browser code would disclose a reusable capability. Email-gating would block anonymous chat and is not identity assurance. | `src/lib/chat-session.ts`; `docs/WEBCHAT_HOSTINGER_TROUBLESHOOTING.md`; `tests/chat-session-security.test.ts`. |
| IR-09 | First-message idempotency and honest error behavior | Network failures can lose responses or trigger retries; a single opaque request ID lets the server recover one intake without duplicating the first message. Never claim a message was saved if its persistence failed. | Do not swallow initial-write errors or turn an uncertain DB operation into a success toast; do not retry with a new identity that creates duplicate CRM records. | `src/app/api/chat/session/route.ts`; `src/lib/contact-policy.ts`; `docs/WEBCHAT_HOSTINGER_TROUBLESHOOTING.md`; retry/idempotency tests. |
| IR-10 | AI is optional for WebChat transport; replies depend on an approved server-side provider, with human follow-up when unavailable | Separate durable message capture from model availability so visitors can contact the team during model outages. Keep provider secrets server-side and disclose actual availability. | Do not fabricate an answer, claim a configured key proves inference, or make anonymous web code call a provider directly. | `src/lib/agents/provider-selection.ts`; `src/lib/chat-orchestrator.ts`; `docs/WEBCHAT_HOSTINGER_TROUBLESHOOTING.md`; AI availability and honest-fallback tests. |
| IR-11 | Multi-provider AI selection with explicit data policy and provider diagnostics | Let the owner select an approved provider and fail honestly when none is usable; different deployments can have different account/billing constraints. | Do not require one vendor when the runtime supports alternatives; do not silently externalize sensitive data or treat gateway health/liveness as readiness. | `.env.example`; `INTEGRATION_CONFIGURATION_GUIDE.md`; `docs/AI_GATEWAY.md`; `KNOWN_ISSUES_AND_BLOCKERS.md` B-006; provider-selection tests. |
| IR-12 | AI agent execution has role, quota, audit and human-approval boundaries | Agents can prepare useful drafts and operate bounded tasks, but commercial, financial, publishing and release commitments require accountable humans. | Do not let an agent self-approve payment, mark its own draft as accepted, publish customer content, or release source code. | `docs/AI_AGENT_HUMAN_LOOP_DELIVERY.md`; `docs/AI_AGENT_TRAINING_ROADMAP.md`; `docs/AI_SOFTWARE_FACTORY.md`; agent policy and approval tests. |
| IR-13 | CRM → discovery → scope/SOW → preview → payment → project → handover lifecycle | Preserve a traceable customer journey and enforce explicit customer/admin decisions at irreversible or commercial steps. | Do not skip scope approval, represent an estimate as a final commitment, charge automatically from a screenshot, or release source before verified payment and approval. | `docs/AI_AGENT_HUMAN_LOOP_DELIVERY.md`; `docs/CLIENT_COMMUNICATION_DOCUMENT_VAULT.md`; `PAYMENT.md`; `tests/business-policies.test.ts`; journey tests. |
| IR-14 | Manual payment channels and a verified Stripe adapter; PayPal/SSLCommerz remain not built | Support payment instructions that can be reconciled, and enable automated settlement only where signed provider evidence is implemented and tested. | Do not mark paid based on a screenshot, SMS claim or browser redirect; do not present unimplemented adapters as enabled. | `PAYMENT.md`; `docs/HOSTINGER_ENVIRONMENT_VARIABLES.md`; payment verification/idempotency tests; `.env.example` explicitly marks unbuilt gateways. |
| IR-15 | SMS/email/WhatsApp/social adapters report `NOT_CONFIGURED`/failure truthfully and keep consent/opt-out state | Delivery depends on provider contracts, sender identities, account approval, callbacks and network behavior outside the repository. Honest states prevent missed messages from being reported as delivered. | Do not pretend the web server owns a phone line, treat arbitrary credentials as proof, or silently switch to a different contact channel. | `src/lib/comms.ts`; `docs/AI_AGENT_HUMAN_LOOP_DELIVERY.md`; `docs/HOSTINGER-ENV-GUIDE.md`; `docs/AI_SOFTWARE_FACTORY.md`; integration tests. |
| IR-16 | Public WhatsApp number/actions are removed while the private provider adapter stays gated | Follow the explicit owner decision for public contact without deleting code needed for an authorized future integration. | Do not advertise a retired phone number or reactivate WhatsApp as a public contact route without owner approval. | `src/lib/site-contact.ts`; `docs/AI_VISIBILITY_POLICY.md`; `docs/AI_SOFTWARE_FACTORY.md`; public-contact tests. |
| IR-17 | Software Factory produces reviewable starter source and a delivery manifest, not an asserted finished product | A generated scaffold is useful as a reproducible starting artifact, but it has not run the customer's exact tests, security review, deployment or acceptance. | Do not claim autonomous completion or deploy arbitrary client code without isolated workspaces, test evidence, provenance and explicit release approval. | `docs/AI_SOFTWARE_FACTORY.md`; `docs/AI_AGENT_HUMAN_LOOP_DELIVERY.md`; factory blueprint, export and approval tests. |
| IR-18 | Media Studio produces scripts, shot plans, captions and renderer-shaped specifications; rendering is provider-gated | Deliver useful planning artifacts without fabricating audio/video output or licensing rights. | Do not mark a job rendered without a real provider result; defer paid render/TTS integrations until provider, license, cost and retention are approved. | `docs/AI_SOFTWARE_FACTORY.md` §2; `THIRD_PARTY_NOTICES.md`; media studio tests; `KNOWN_ISSUES_AND_BLOCKERS.md` B-005. |
| IR-19 | Feed Hub parses RSS/Atom/JSON server-side with SSRF and content-sanitization controls | Ingest public signals without letting feed URLs reach private network resources or republishing untrusted markup as trusted content. | Do not fetch arbitrary redirects/hostnames without controls or copy source text as original marketing content. | `docs/AI_SOFTWARE_FACTORY.md` §3; `src/lib/feeds/parse.ts`; `src/lib/safe-fetch.ts`; feed parsing/security tests. |
| IR-20 | Calls & SMS console logs calls/click-to-call and uses a device SMS gateway only when configured | A web app cannot place a telephone call without an actual telephony provider/device. The UI should distinguish an operator action from server-executed telephony. | Do not simulate a call or claim a sent SMS if no connected device/provider accepted the request. | `docs/AI_SOFTWARE_FACTORY.md` §4; `src/lib/telephony.ts`; telephony tests. |
| IR-21 | Upload validation and quarantine are explicit, but no external malware scan is claimed | Validate file types and hostile payload patterns early and preserve a quarantine state while being honest that static checks are not antivirus. | Do not claim a file is malware-free without a selected scanner and recorded scan evidence. | `SECURITY.md`; `docs/AI_WORKFORCE_AUDIT.md`; `tests/business-policies.test.ts`; requirements register R-023 (historical status). |
| IR-22 | Backup and restore tooling is separate from the app's normal write path and requires real host scheduling/drills | Recovery requires an independent copy, measured restore process and acceptable RPO/RTO, not just a script in Git. | Do not write “backup successful” from an unexecuted schedule or run destructive commands on production during an audit. | `docs/BACKUP_AND_RESTORE.md`; `KNOWN_ISSUES_AND_BLOCKERS.md` B-004; backup/restore tests. |
| IR-23 | GitHub CI validates production MySQL migrations/build; it does not deploy Hostinger | Reproducible checks should use the same database engine as production; deployment ownership remains with the selected Hostinger Git integration. | Do not let a green CI run masquerade as a production deployment or add a competing SSH deployer. | `.github/workflows/ci.yml`; `docs/HOSTINGER_DEPLOYMENT.md`; MySQL schema/migration, build and smoke gates. |
| IR-24 | Dependency audit findings are release gates; the review branch updates Next but does not suppress the remaining upstream advisory | Security scans should remain visible and reproducible, including unresolved advisories; widening thresholds could hide a real risk. | Do not lower the audit threshold, add an unreviewed exception, or claim `picomatch@4.0.7` is fixed. | `docs/REPOSITORY_AUDIT_2026-11-17.md` §6; `package-lock.json`; `.github/workflows/ci.yml` dependency audit step. |
| IR-25 | Research-source adoption is filtered by license, maintenance and actual feature gap; ideas may be reimplemented as original code | Protect the project's commercial rights, avoid importing unnecessary dependencies, and adapt designs to local policies and data models. | Do not copy from repositories with no license or incompatible copyleft; do not add components already present without a measured need. | `docs/research/FEATURE_GAP_AND_ADOPTION_PLAN.md`; `docs/research/GITHUB_LICENSE_MATRIX.md`; `docs/research/GITHUB_SOURCE_CATALOG.csv`. |
| IR-26 | Compliance and production status distinguish code presence from provider/legal/host acceptance | Legal duties, provider agreements, real credentials and production evidence depend on the owner, provider and target jurisdiction. | Do not certify compliance, deliverability, restore readiness or production release based only on source review or CI. | `SECURITY.md`; `KNOWN_ISSUES_AND_BLOCKERS.md`; `docs/REPOSITORY_AUDIT_2026-11-17.md` §5; owner/legal acceptance required. |
| IR-27 | SMS opt-out keywords are parsed deterministically before AI, persisted, and enforced by outbound SMS dispatch and retries | Consent withdrawal must not depend on probabilistic language classification; `START` cannot silently re-enable sends. The shared communication state also inhibits scheduled follow-ups that consult it. | Do not route STOP through discovery/AI, allow a queued retry to bypass opt-out, or silently treat START as fresh consent. Keep exact keyword matching to avoid suppressing ordinary text; explicitly exempt a client-requested portal sign-in OTP. | `src/lib/sms-policy.ts`; `src/app/api/webhooks/sms/route.ts`; `src/lib/comms.ts`; `tests/sms-policy.test.ts`; provider/jurisdictional behavior remains unverified. |

## Current review-branch repairs: explicit rationale

| Change | Reason | Intended invariant | Test/evidence |
|---|---|---|---|
| Normalize missing/blank email in exact first-contact replay | Anonymous chat stores `null`, while a retried browser request can serialize an omitted value as `""`; strict comparison blocked a valid recovery. | Same request ID + same visitor + equivalent blank contact may recover; a different non-empty address cannot. | `tests/chat-session-security.test.ts`; `tests/tech360-messaging-repair.test.ts`. |
| Require and persist the first message before reporting session success | Empty sessions are not useful intake, and swallowing write errors loses customer input while the UI reports success. | Empty input is rejected; failed initial write returns an error; the same request can retry idempotently. | `tests/tech360-messaging-repair.test.ts`; route behavior in `src/app/api/chat/session/route.ts`. |
| Treat thread fetch as a recoverable read after a successful session | A read failure must not reverse the fact that the server accepted the session, or hide the open conversation. | Keep the thread/composer visible and show a connection issue; do not tell the visitor that a successfully persisted initial message failed. | `src/components/site/ChatWidget.tsx`; targeted chat tests. |
| Remove unconditional instant-AI promise | AI provider availability and successful inference are external runtime outcomes, not guaranteed by WebChat. | UI describes persistence and optional AI/human response separately. | `tests/tech360-messaging-repair.test.ts`. |
| Update resolved Next packages while retaining the strict audit gate | The current lock resolved a Next version with moderate advisories; compatible update removes those while the remaining transitive issue stays visible. | No audit suppression; build/CI must re-verify the updated lock before release. | `package-lock.json`; `docs/REPOSITORY_AUDIT_2026-11-17.md` §6. |

## Review and change-control rule

When a future feature or security-sensitive behavior is added, update the row for its subsystem (or add a focused design decision) with: **problem/requirement, chosen approach, rejected alternative and reason, risks/trade-offs, evidence/tests, and what remains unverified**. Keep this record value-free: no credentials, customer data or private production URLs. A code change without an evidence-backed rationale is not a production-completion claim.
